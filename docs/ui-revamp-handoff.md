# UI 개편 인수인계 — `feat/ui-revamp`

> 상태: 진행 중 (원격 푸시됨)
> 최종 갱신: 2026-08-29
> 브랜치: `feat/ui-revamp` (`a7d9ad2` 기준, 커밋 4개)

대시보드 UX 개편 작업의 중간 인수인계 문서. **왜 그렇게 만들었는지**와 **다음에 뭘 해야 하는지**를 남긴다. 무엇을 바꿨는지는 커밋 메시지에 있으므로 여기서 반복하지 않는다.

## 1. 이 개편이 풀려던 문제

원래 화면은 "잘 정리된 태스크 툴"이었고, 사용자가 원한 건 **관제탑(control tower)** 이었다. 진단은 레이아웃이 아니라 구조였다.

**아무 일도 없을 때 화면을 가장 많이 쓰는 구조.** `AI 팀` 밴드가 "할당된 작업 없음"을 두 번 말하고, `오늘 요약` 카드가 "0 Task"를 말하고, 그 아래 빈 리스트가 있었다. 세 영역이 각각 "없다"고 말하려고 자리를 차지했다.

그래서 전체를 관통하는 원칙은 하나다: **공간은 활동량에 비례한다.**

## 2. 확정된 설계 결정

되돌리기 전에 왜 그렇게 됐는지 알아야 하는 것들.

### 관제탑은 헤더에 상주하고, 항상 한 줄이다

`components/app-header.tsx` → `features/agents/components/control-tower.tsx`

섹션으로 두면 스크롤에 사라지고, 그러면 그건 상태에 *관한 카드*지 계기판이 아니다. 헤더에 붙어야 관제탑이 된다.

한때 실행 중인 Agent마다 행이 펼쳐지게 만들었다가 걷어냈다. **바로 아래 리스트가 같은 질문에 더 잘 답한다.** 관제탑에는 리스트가 스스로 말할 수 없는 것만 남긴다 — 뭔가 돌고 있나, 얼마나 조용했나, 오늘 요약, 경보.

### 진행률을 퍼센트로 표시하지 않는다

`features/tasks/components/step-track.tsx`

**이 시스템에는 % 신호가 없다.** Step은 `RUNNING`이라고만 보고하지 "37% 완료"를 주지 않는다. 차오르는 바는 전부 UI가 지어낸 애니메이션이 되고, 그건 프로세스가 멈춰도 90%라고 우기는 종류의 지표다.

대신 **마일스톤 레일**이다. 노드 개수와 위치가 Task 생애 내내 변하지 않는다 (`workflow.steps`가 생성 시점에 전부 `PENDING`으로 만들어지므로 경로를 미리 알 수 있다). 진행 중인 구간은 sweep 모션으로 "작동 중"을 말하되 분수를 주장하지 않는다.

- **`시작` 노드가 있는 이유**: 없으면 1-Step Task(리뷰 전용)가 시작하자마자 트랙 전체를 채워서 "완료"처럼 보인다. 실제로 그렇게 만들었다가 고쳤다.
- **구간 폭을 상태에 따라 바꾸지 않는 이유**: 실행 중 구간에 여분 폭을 주면 진행에 따라 노드가 좌우로 움직인다. 마일스톤의 의미가 사라진다.
- **홈(groove)을 까는 이유**: 없으면 아직 안 지난 구간이 거의 안 보여서 노드가 허공에 뜬 것처럼 읽힌다.

### 정지 경고는 "말한 적 있는데 끊긴 것"만

`features/tasks/components/activity-trace.tsx`

로그 도착이 유일한 진짜 작업 증거라서 지진계처럼 그린다. 그런데 **에이전트마다 출력 패턴이 정반대다.**

|        | 패턴            | 실측                                                       |
| ------ | --------------- | ---------------------------------------------------------- |
| Codex  | 꾸준히 스트리밍 | 2분42초 동안 282줄                                         |
| Claude | 통째로 버퍼링   | 55초 실행 → 첫 출력 54초째<br>179초 실행 → 첫 출력 178초째 |

Claude는 **실행 시간과 무관하게 마지막 1초에 전부 쏟아낸다.** 그래서 단순 침묵 임계값(초기 30초)은 정상 Claude 작업마다 경고를 띄웠다.

현재 규칙: **출력이 나온 적 있고(≥1줄), 그 뒤 90초 이상 침묵**일 때만 경고. 한 번도 안 나온 건 정지가 아니라 버퍼링이다. `system` 로그(라우터 자기 로그)는 제외 — 카운트하면 감지하려던 침묵을 가린다.

이 규칙은 실측 데이터로 검증했다: 정상 Claude 실행 3건 무경고, 고아 프로세스 시뮬레이션 100초+에서 경고.

### 완료 행에는 레일 대신 상태 색

한때 완료 행에도 마일스톤 레일을 넣었다. 정보로서는 진짜였지만(어느 Agent가 돌았나, 어디서 멈췄나) **회색 레일 20개가 세로로 쌓이면 리듬만 깨진다.** 끝난 Task에서 훑을 가치가 있는 건 결과 하나고, 나머지는 상세 페이지가 한 클릭 거리에 있다.

### 제목은 의도 우선, 그리고 항상 고칠 수 있어야 한다

`packages/shared/src/title.ts`

기존 로직은 파일명을 제목으로 승격시켜서 `01.src\home\tools-hub\...smoke.txt, ai…` 같은 게 나왔다. 원인은 정규식 문자 클래스에 두 종류 구분자가 다 들어있어서 **leaf 파일명을 잡겠다는 패턴이 경로 전체를 삼킨** 것.

지금은 첫 줄의 의도를 제목으로 쓰고 경로는 제거한다. 다만 **휴리스틱은 가끔 틀리고, 그때 고칠 수 있는 게 안 틀리는 것보다 중요하다** — 생성 폼 입력란과 `PATCH /api/tasks/:id`(rename)가 그래서 있다.

> **함정**: 이 파일에서 백슬래시 이스케이프(`\\`)를 쓰지 말 것. 한 번 `[\\/]`가 `[\/]`로 뭉개져 Windows 경로를 통째로 놓친 적이 있다. `BACKSLASH = String.fromCharCode(92)` 상수를 쓴다.
>
> **함정 2**: 보이지 않는 문자를 지울 때 `\p{Cc}`에 **개행이 포함된다.** 한 번 이걸로 여러 줄 지시문이 한 줄로 뭉개져 "첫 줄을 제목으로" 규칙이 무너졌다. 현재 `INVISIBLE`은 `\n\r\t`를 명시적으로 제외한다.

### Task 폴링은 앱 전체에 하나

`features/tasks/hooks/use-task-list.tsx`

이전엔 소비처마다 `setInterval`을 돌려서 **태스크 상세 화면 하나에서만 동일 엔드포인트를 3초마다 2번** 긁었고 설정 화면이 세 번째였다. 프로바이더로 승격하고, 탭이 숨겨지면 폴링을 완전히 멈추며, 실행 중이면 2초 / 유휴면 10초로 적응한다.

## 3. 서버 쪽에서 고친 것 하나

`apps/server/src/tasks/recover-interrupted.ts`

**서버가 죽으면 실행 중이던 Task가 영구 박제되는 버그가 원래 있었다.** Agent 실행은 서버가 소유한 자식 프로세스이고 취소 핸들은 메모리에만 있다. 서버가 종료되면 자식은 같이 죽는데 저장된 Task는 여전히 `RUNNING`/`REVIEWING`이다. 그리고 두 출구가 모두 막혀 있었다:

```
cancelTask  → 죽일 프로세스가 없음 → 409 "실행 중인 프로세스를 찾지 못했습니다"
deleteTask  → RUNNING/REVIEWING이면 거부
```

이제 부팅 시 이런 Task를 `FAILED`로 정리한다. `CANCELLED`가 아닌 이유: 사용자가 중단한 게 아니므로 `확인 필요`에 떠서 눈에 띄고 재실행할 수 있어야 한다.

> **주의**: `tsx watch`가 `packages/shared`를 감시하므로, **Task 실행 중에 shared를 리빌드하면 서버가 재시작되며 그 Task가 끊긴다.** 실제로 T-21이 이렇게 죽었다. 작업 실행 중에는 shared 빌드를 피할 것.

## 4. 남은 작업

### (1) `resultLine` fallback 정리 — 작고 확실함

`features/tasks/components/task-row.tsx:92-119`

둘째 줄 문구가 상태를 되풀이하는 fallback이라 **셋 중 한 경우에만 참이다.**

| READY 도달 경로         | 리뷰 실행              | "지적 사항 없음"            |
| ----------------------- | ---------------------- | --------------------------- |
| `purpose: "review"`     | 실행됨                 | 참                          |
| `implement` + diff 없음 | SKIPPED (`NO_CHANGES`) | 거짓 — 내려진 적 없는 판정  |
| `purpose: "analyze"`    | 리뷰 스텝 자체가 없음  | 거짓 + 진짜 결과물을 밀어냄 |

같은 fallback이 다른 곳에서도 샌다:

- `CANCELLED` — 배지 `취소됨` + 문구 `실행 취소됨` (순수 중복)
- `REVIEW_FAILED` — 배지 `리뷰 실행 실패` + 문구 `검토 지적 사항 있음` (**서로 모순**, 리뷰가 죽어서 판정이 없는 건데 "지적 있음"이라고 함)
- `FAILED` (error 비어있음) — 배지 `실행 실패` + 문구 `실행 실패` (반복)

**결정된 방향**: 완료 그룹을 **통째로** 한 줄로. 그룹 안에서 상태별로 자르면(READY만 접고 CANCELLED는 남기면) 행 높이가 52/72px로 교대해서 진짜 들쭉날쭉해진다. 상태는 이미 3px 레일 + 배지가 지고 있으므로 잃는 정보는 사실상 없다.

**주의**: `taskActivityPhrase` 자체는 건드리지 말 것. 태스크 상세 히어로와 `ActiveTaskCard`도 쓰는데 거기서는 경쟁하는 정보가 없어 문구가 제 몫을 한다. 수정은 `task-row.tsx` 안에서.

### (2) 논의방 UX — 원래 목적지

`docs/discussion-room-proposal.md`

이 UI 개편의 애초 동기는 **"이 방식이 마음에 들면 논의방도 같은 UX로 구현한다"** 였다. 이제 시각 언어가 잡혔으므로 그걸 논의방에 적용할 차례다.

논의방 설계에서 **이미 논의되고 폐기된 것**을 다시 꺼내지 말 것:

- **레인/체인 뷰 (폐기됨)** — Claude 레인 → Codex 레인으로 카드가 넘어가는 칸반. 리뷰 전용·분석 전용 Task가 체인을 안 타고, 역할 설정이 바뀌면 레인이 통째로 빈다(기본값은 implementer=Claude, reviewer=Codex라 우연히 체인처럼 보일 뿐이다). 구조가 데이터를 배신한다.
- **대신 채택된 것** — 카드가 무대이고 **거기 앉은 캐릭터가 교대**한다. 단계 수가 1이든 2든 분기가 없다.

논의방에 그대로 옮길 수 있는 것: 캐릭터 상태 모션(`agent-character.tsx`), 마일스톤 레일(§7의 4단계 흐름이 그대로 매핑됨), 활동 트레이스.

### (3) 검토만 하고 안 정한 것

- **픽셀아트 도입 여부** — 참고: [Star Office UI](https://github.com/ringhyacinth/Star-Office-UI). 코드는 MIT지만 **아트 에셋은 비상업 한정**이라 자체 제작 필요. 한글 픽셀 폰트(`ark-pixel`, OFL)는 자유롭게 사용 가능. 현재는 기존 `AgentIcon` 글리프에 모션만 입힌 상태이고, 스프라이트로 교체하려면 `agent-character.tsx` 내부만 바꾸면 되도록 경계를 잡아뒀다.
- **`generateTitleFromInstruction`의 완료 시점 승격** — `result.summary`에서 제목을 다시 뽑자는 안이었으나 **폐기**. 그 필드는 정제된 요약이 아니라 stdout 마지막 4000자다(리뷰 Step은 통째로 JSON). 대안: 리뷰 프롬프트가 이미 구조화된 JSON을 요구하므로 거기에 `title` 필드를 추가하면 추가 호출 0으로 AI 제목을 얻을 수 있다. 단 리뷰가 있는 Task에만 적용된다.

## 5. 개발 환경 메모

```bash
pnpm run dev          # web :9913 / server :9914
pnpm -r run typecheck
pnpm --filter @ai-task-router/web lint
pnpm run format:check
pnpm --filter @ai-task-router/web build   # dev 서버를 먼저 끌 것 (.next EPERM)
```

- **`next build`를 반드시 돌릴 것.** `useSearchParams()`가 Suspense 없이 쓰이면 **dev는 통과하고 build만 실패한다.** 실제로 한 번 걸렸다 (`app/page.tsx`의 Suspense 경계가 그래서 있다).
- 검증은 typecheck / lint / prettier / build 네 개를 모두 돌린다.
