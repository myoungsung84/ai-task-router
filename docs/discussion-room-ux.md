# 논의방 UX 1차 설계안

> 상태: 1차 샘플 (구현 전)
> 작성일: 2026-08-29
> 기준 문서: `docs/discussion-room-proposal.md`
> 시각 언어: `docs/ui-revamp-handoff.md`

기획 초안(`discussion-room-proposal.md`)의 §8 채팅방 UX를, UI 개편에서 확정된 시각 언어 위에 올린 1차 안. **화면을 어떻게 그릴지**만 다루고 기능 범위는 기획서를 따른다.

## 1. 이 설계가 풀어야 하는 구조적 사실

기획서 §2가 UX를 결정한다.

> 채팅은 사람이 빠르게 읽기 위한 요약 화면이고, AI는 채팅 요약이 아니라 최신 원본 문서를 읽고 판단한다.

여기 함정이 두 개 있고, 둘 다 흔한 선택지다.

- **문서를 링크 뒤에 숨기면** — 진짜 판단 기준이 화면에서 사라진다. 개편 전 대시보드가 "관제탑이 아니라 상태에 관한 카드"였던 것과 같은 실패다.
- **채팅과 문서를 반반 나누면** — "문서 에디터에 채팅이 붙은 화면"이 되고, §8의 _회의 관리 UI를 전면에 내세우지 않는다_ 를 정면으로 어긴다.

그래서 관제탑에서 쓴 원칙을 그대로 가져온다: **사라지지 않되, 아래 화면이 스스로 말할 수 없는 것만 이고 있는다.**

## 2. 전체 구조 — 작업과 논의는 별도 영역

기획서 §10이 "논의방은 코드 Task와 별도 도메인"이라고 못 박았으므로 최상위에서 갈린다.

```
┌──────────────────────────────────────────────────────────┐
│ ◆ AI Task Router   [작업] [논의]        🌓  ⚙  [+ 새 논의] │
├──────────────────────────────────────────────────────────┤
│ 관제탑 — 탭에 따라 내용이 교대, 항상 한 줄               │
└──────────────────────────────────────────────────────────┘
```

`components/app-header.tsx`에는 현재 탭이 없다 (브랜드 링크 + 우측 컨트롤뿐). 탭을 추가하면서 두 가지가 따라온다.

|         | 작업 탭     | 논의 탭                                |
| ------- | ----------- | -------------------------------------- |
| 관제탑  | 지금 그대로 | 발언 중인 AI · 미결정 쟁점 · 조율 필요 |
| 주 버튼 | `새 작업`   | `새 논의`                              |

**관제탑의 계약은 바꾸지 않는다** — 헤더에 상주하고, 조용하면 한 줄만 차지하고, 아래 목록이 못 하는 말만 한다. 내용만 도메인에 맞게 교대한다.

이 분리가 기획서 §10을 화면으로 보증한다는 점이 중요하다. 논의 영역에는 파일 수정·테스트·브랜치·커밋을 실행할 UI가 **애초에 존재하지 않는다.** 규칙을 문서로만 지키는 것보다 강하다.

공유하는 것은 셋뿐이다: 헤더, 관제탑 자리, 그리고 캐릭터·레일·활동 트레이스의 시각 언어.

### 논의 헤더 — 한 줄 상주

제목 · 상태(`진행 중`/`조율 중`/`종료`) · 참여자 캐릭터 · 문서 버전과 최종 갱신. 기획서 §8 상단 요구(제목·상태·참여자·저장소)를 만족시킨다.

### 저장소는 여러 개가 기본이다

`features/discussions/components/repo-scope.tsx`

1차 스케치는 Task 리스트의 프로젝트 칸을 그대로 빌려 `tools-hub +2`로 그렸다. **틀렸다.** Task는 한 곳에서 실행되지만 논의는 대개 **여러 곳이 어떻게 얽히는지**가 안건이다 — 저쪽 저장소의 미러를 감안해 이쪽 수집기를 줄일 수 있느냐 같은 것. 그래서 저장소 집합 자체가 질문의 일부이고, 먼저 등록됐다는 이유로 하나를 대표로 승격시키면 **없는 주(主) 저장소를 발명하는 것**이 된다.

전부 같은 크기로 나열한다. 기획서 §4가 이 목록을 **AI의 조사 경계**로도 쓰기 때문에 더 그렇다 — 여기 없는 저장소는 AI가 안 본다. 하나 빠져 있으면 방 안의 모든 답변이 보이는 것보다 좁다는 뜻이라, 훑어서 확인할 수 있어야 한다.

리스트 행에서만 2개 + 개수로 자른다. 열 너비를 제일 넓은 논의가 정하게 두지 않으려는 것뿐이고, 방 헤더는 전부 편다.

### 문서 레일 — 접힌 채 상주

기본은 최신 요약 블록에서 뽑은 한 줄: `합의 3 · 쟁점 2 · v15`. 펼치면 요약 전문(확인된 사실 / 합의 / 미결정 / 사용자 결정), 그 아래 `전체 기록` 토글로 append 로그 원문.

§8이 요구한 _보조 영역: 현재 합의 내용과 남은 쟁점의 자동 요약_ 은 접힌 한 줄이 이미 만족한다. 펼치는 건 깊게 볼 때뿐이므로 일반 채팅 경험이 깨지지 않는다.

### 메시지는 기획서보다 더 짧게

§8은 `3~5줄`을 말하지만 이 안은 **결론 1줄 + 근거 최대 2줄 + 참고 링크**로 조인다.

채팅에 근거를 3~5줄 풀면 사람이 그걸 읽고 판단하기 시작하고, 그러면 "문서가 단일 기준"이 말로만 남는다. 짧을수록 `상세 #47`을 누르게 되고, 그게 기획 의도다.

## 4. AI 발언 — 카드가 무대, 캐릭터가 교대

UI 개편에서 레인/체인 뷰를 버리고 채택한 구조를 그대로 쓴다. 논의방에서는 근거가 더 강하다: **AI가 추가·강퇴되면(§8) 레인은 통째로 생겼다 없어지지만, 무대는 참여자 수가 변해도 흔들리지 않는다.**

### §7의 5단계가 마일스톤 레일에 그대로 매핑된다

```
시작 ── 문서 읽음 ── 검토 ── 기록 ── 버전 확인 ── 요약 게시
```

- **`시작` 노드가 필요한 이유** — 태스크 쪽과 같다. 없으면 첫 단계에 진입하자마자 트랙이 차서 끝난 것처럼 보인다.
- **퍼센트는 여전히 안 쓴다** — 단계는 이산적이고 `37%`에 해당하는 신호가 없다. 진행 중 구간은 sweep 모션으로 작동을 말하되 분수를 주장하지 않는다.
- **이 레일이 규칙을 증명한다** — 첫 노드가 문자 그대로 `문서 읽음`이라, §2의 "AI는 채팅 요약이 아니라 원본 문서를 읽는다"가 지켜지는 걸 사용자가 눈으로 본다.

### 게시되면 레일은 접힌다

작성 중에만 보이고, 게시 후에는 그냥 메시지가 된다. 완료 행에 레일을 남기지 않기로 한 것과 같은 판단이고, 세로로 계속 쌓이는 채팅에서는 더 치명적이다.

## 5. 반복 방지는 메시지가 아니라 캐릭터 상태로

기획서 §2의 `입장 유지`를 **메시지로 게시하면 무한 논의 방지 장치가 무한 스크롤을 만든다.** "Codex: 입장 유지"가 계속 쌓인다.

대신 참여자 캐릭터의 상태로 표현한다. 헤더의 해당 캐릭터가 `입장 유지`를 이고 있고, 새 근거가 들어오면 풀린다. 채팅은 조용해지고 정보는 잃지 않는다. `agent-character.tsx`에 상태 케이스 하나를 늘리는 수준이다.

정정도 같은 원칙 — 원래 메시지를 지우지 않고 자리에 둔 채 톤을 낮추고 `→ 정정됨` 앵커를 단다(§8).

## 6. 영속화 — append-only 마크다운

**결정됨**: 원본 논의 문서는 마크다운 파일 하나에 계속 append 한다.

### 파일은 프로젝트 저장소 밖에 둔다

기획서 §10이 "논의 중 프로젝트 파일 수정 안 함"이라고 못 박았다. 원본 문서를 관련 저장소 안에 두면 그 규칙에 예외를 파야 하고, 그 예외는 나중에 "이 파일은 되는데 저건 왜 안 되냐"로 번진다.

두 가지를 다른 개념으로 둔다.

|                      | 무엇                                         | 쓰기     |
| -------------------- | -------------------------------------------- | -------- |
| 관련 프로젝트 저장소 | AI의 조사 범위 (§4)                          | 없음     |
| 논의 기록 저장소     | Router 기본 데이터 디렉터리 또는 지정된 위치 | Router만 |

**경로를 코드에 박지 않는다.** `data/discussions/<id>.md`는 **기본값**이고 제품의 고정 경로가 아니다. 실제 환경에서는 공식 기록이 `SRC/work-log/<폴더>` 같은 다른 곳에 있고, 그렇다면 파일명·하위 폴더·문서 양식도 그쪽 규칙을 따라야 한다. 저장 계층은 `DiscussionDocumentStore` 성격의 어댑터로 분리하고, **사용자가 지정한 허용 루트 아래 상대 경로만** 쓴다 — AI가 임의의 절대 경로를 만들 수 있으면 §4의 조사 경계가 의미를 잃는다.

회사 기록 샘플을 확인하기 전에는 마크다운 헤더·파일명·색인 형식을 확정하지 않는다.

### 요약도 append 하고, 마지막 것이 유효하다

§5에 긴장이 하나 있다. 앞문장은 append 그 자체지만("상대가 쓴 내용을 수정하지 않고 자신의 새 항목으로 추가"), 뒷문장은 갱신이다("상단의 확인된 사실·합의·미결정 요약은 갱신한다"). 순수 append로는 상단 요약을 고칠 수 없다.

해결: 요약도 블록으로 append 하고 **화면은 마지막 요약 블록만 렌더한다.**

```
## 요약 v14 · 14:02
확인된 사실 / 합의 / 미결정 / 사용자 결정
---
## Codex 상세 의견 #47 · 14:05
...
---
## 요약 v15 · 14:06        ← 최신. 문서 레일이 읽는 것
```

파일은 끝까지 append-only이고, §5 두 문장이 모두 성립하며, §5가 요구한 `변경 이력`이 별도 기록 없이 파일 자체로 남는다.

### 숫자는 셋이고, 겸용하지 않는다

1차 초안은 `version` 하나로 다 했다. 세 역할이 서로 반대 방향으로 움직여서 성립하지 않는다.

| 이름             | 역할                      | 언제 바뀌나           |
| ---------------- | ------------------------- | --------------------- |
| `revision`       | 충돌 감지 (§7 4단계)      | **모든 append마다**   |
| `entryRef`       | 영구 앵커 (`상세 #47`)    | **절대 안 바뀜**      |
| `summaryVersion` | 화면이 보여주는 요약 버전 | 요약 블록이 붙을 때만 |

하나로 묶으면 셋 중 둘이 반드시 틀린다. `revision`이 안 움직이면 충돌을 못 잡고, `entryRef`가 움직이면 예전 메시지의 링크가 썩고, `summaryVersion`이 매 append마다 올라가면 요약이 그대로인데 레일이 깜빡인다.

**앵커는 문서가 발급한다.** 쓰는 쪽이 고르지 않는다 — 같은 번호가 두 항목에 나가면 그걸 가리키던 링크가 전부 조용히 어긋난다.

### 이 결정이 UX에 사주는 것

- **앵커가 흔들리지 않는다.** §6이 요구하는 "채팅 메시지 ID ↔ 문서 항목 연결"이 공짜다. 한 번 쓰인 항목은 위치가 영원히 변하지 않으므로 `상세 #47` 링크가 깨질 일이 없다.
- **§7 4단계 `버전 확인`이 실제로 보인다.** 충돌 감지가 "내가 읽은 뒤로 파일 끝에 뭐가 붙었나"라서, 붙었으면 다시 읽고 조정하는 과정이 레일 위에 그대로 나타난다. DB였으면 서버에서 조용히 처리되고 화면엔 안 나타났을 단계다.

## 7. 발언권과 턴

`features/discussions/turn-engine.ts`

누가 언제 말하는지를 정하는 규칙. **기획서에 이미 있는데 다른 이름으로 적혀 있다** — §2의 무한 논의 방지는 내용 규칙처럼 쓰여 있지만 실제로는 발언권 규칙이다.

> 새 근거 없이 입장이 유지되면 반복 답변 대신 `입장 유지`로 문서에 표시한다.

그래서 답은 "자동이냐 수동이냐"가 아니다. **자동으로 돌리되, 할 말 없으면 조용히 넘어간다.**

### 게이트 두 개

**게이트 1 — Router: 이 발언이 턴을 유발하는가**

§6이 사용자 발언을 `의견`과 `결정`으로 나눠둔 것이 그대로 쓰인다.

| 사용자 발언        | 턴                         |
| ------------------ | -------------------------- |
| 의견 · 질문 · 반박 | 돈다                       |
| **결정**           | **안 돈다.** 문서에 기록만 |
| 애매               | Router가 되묻는다 (§6)     |

결정에 AI들이 각각 "네, 합리적입니다"라고 답하면 그게 정확히 §2가 금지한 **근거 없는 빠른 동조**다. 결정에는 아무도 대꾸하지 않는 것이 맞다.

**게이트 2 — 각 AI: 새로 할 말이 있는가**

§7대로 문서를 읽고 검토한 뒤, 새 사실·코드·측정값·새 논리가 있으면 발언하고 없으면 `입장 유지`. 판단은 항상 하고 출력만 갈린다. 침묵이 세로 공간을 안 먹는 건 §5 덕분이다.

### 라운드

**턴은 사용자 발언에서만 시작된다.** AI 발언은 다른 AI의 턴을 유발하지 않는다. §2의 무한 논의 방지를 내용이 아니라 **구조로** 한 번 더 막는 것이다.

**한 라운드 = 참여자 전원 1회.** 끝나면 무조건 사용자에게 돌아온다. 재반박이 필요하면 `계속`을 누르면 다음 라운드가 돈다 — 한 번의 클릭으로 사람이 항상 루프 안에 남는다.

**첫 라운드만 병렬, 이후 순차.** 첫 라운드에는 engage할 상대 의견이 아직 없으므로 순서가 아무것도 사주지 않고, 대신 **서로 앵커링되지 않은 유일한 독립 읽기**를 잃는다. 둘째 라운드부터는 §2가 "다음 AI는 갱신된 문서를 기준으로"라고 요구하므로 순서가 필요하다.

> **정정**: 초안은 "append-only라 병렬 쓰기가 공짜"라고 썼다. **틀렸다.** 그건 _논리적_ 충돌이 없다는 뜻이었고(아무도 남의 글을 덮어쓰지 않는다) 거기서 _물리적_ 쓰기 안전으로 미끄러졌다. 같은 파일에 여러 프로세스가 동시에 append하면 순서와 버전이 어긋난다. append-only는 쓰기를 **파괴적이지 않게** 만들 뿐, 두 writer가 순서에 합의하게 만들지 않는다 — 그리고 이 문서의 가치는 순서가 곧 기록이라는 데 있다.

### 병렬은 판단까지, 쓰기는 직렬

병렬 라운드에서 지키려던 속성(앵커링 없음)은 **판단 단계에만** 필요하다. 쓰기까지 병렬일 이유는 없다.

1. 각 AI의 읽기와 판단을 **같은 기준 revision**에서 병렬 실행한다.
2. 결과를 Router가 모은다.
3. Router 한 곳에서 상세 항목을 **결정적 순서로 직렬 append** 한다.
4. 모든 상세 항목이 들어간 뒤, 그때의 문서를 기준으로 **요약 블록을 한 번** append 한다.

4단계가 마지막인 이유: 요약은 자기 밑에서 아직 움직이는 문서를 대상으로 쓰면 안 된다. 그래서 요약은 먼저 끝낸 AI가 아니라 **Router가** 쓴다.

기본 순서는 **직전 라운드에 발언하지 않은 쪽 먼저**. 한쪽이 계속 주도하는 걸 막고, 판단이 안 들어가서 예측 가능하다.

### 말로 하는 턴 조작

§2가 `채택`·`반박`·`동의` 버튼을 금지했으므로 턴 조작도 버튼이 아니다. 세 가지가 서로 다르다.

| 사용자 발언                 | 의미                    | 게이트 2 |
| --------------------------- | ----------------------- | -------- |
| "코덱스가 **먼저** 말해봐"  | 순서만 바꿈. 둘 다 발언 | 유지     |
| "코덱스**만** 봐줘"         | 참여자 제한             | 유지     |
| "코덱스 **어떻게 생각해?**" | 지목 — 강제 턴          | **무시** |

가운데와 아래의 차이가 중요하다. 순서를 지정했는데 코덱스가 `입장 유지`로 넘어가는 건 정상이다(할 말이 없는 게 사실이니까). 하지만 **직접 물었는데 침묵하면 그건 고장으로 읽힌다.** 그래서 지목만 게이트를 뚫는다.

지목받았는데 새 근거가 없으면 **"새 근거가 없어 입장을 유지한다"고 말한다.** 침묵도 아니고 없는 논거를 지어내지도 않는다 — 후자가 §2가 금지한 것이다.

### 지시문은 문서에 남기지 않는다

"코덱스가 먼저"는 `사용자 의견`이 아니다. 논의 내용이 아니라 라우팅이다. §6대로 기록하면 문서에 이런 게 쌓인다.

```text
사용자 의견
- 코덱스가 먼저 발언했으면 한다.   ← 아무 근거도 아님
```

한 메시지에 둘이 섞일 수 있다 — "재생성 비용이 더 클 것 같은데, **코덱스가 먼저** 봐줘". Router가 가른다: **내용은 문서로, 지시는 큐로.**

### 종료 조건

| 조건                         | 결과                                 |
| ---------------------------- | ------------------------------------ |
| 전원 `입장 유지` + 쟁점 남음 | `조율 중` 전환, 관제탑에 `조율 필요` |
| 전원 `입장 유지` + 쟁점 없음 | 조용히 대기 (종료는 §9대로 사용자만) |

앞줄이 논의 쪽의 `확인 필요`다. 스스로 멈췄고 사람이 개입해야만 다시 움직이는 유일한 상태다.

**그리고 개입하면 실제로 풀려야 한다.** 결정은 턴을 돌리지 않지만(게이트 1) 그렇다고 아무 일도 없는 게 아니다 — 문서에 append되고, 요약 블록을 새로 만들고, `조율 중`을 해제한다. `조율 중`의 의미가 "당신을 기다리는 중"이므로 사용자가 말한 순간 그 조건이 사라진다. 쟁점이 남아 있을 수는 있지만 방이 멈춰 있는 건 아니다.

초안 구현은 결정을 받아도 상태를 다시 계산하지 않아서, **사람이 개입해도 `조율 중`이 안 풀렸다.** 스스로 설계한 탈출구를 막아둔 셈이라 고쳤다(`statusAfterDecision`).

### 턴 상태는 문서에 넣지 않는다

`{ round, queue, pending }`은 Router가 소유하는 **휘발성** 상태다. 문서는 append-only 기록이라 성격이 다르다. 서버가 재시작되면 진행 중이던 라운드는 버리고 사용자에게 돌려준다 — `recover-interrupted.ts`가 끊긴 Task를 `FAILED`로 정리하는 것과 같은 판단이다.

> **다만 그 유추는 큐까지만 맞다.** 끊긴 Task는 `RUNNING → FAILED`로 되돌릴 수 있지만 **이미 append된 항목은 되돌릴 수 없다.** 지우는 것이 이 저장 방식의 유일한 금지 사항이기 때문이다.

그래서 큐와 별개로 **멱등성 키**가 필요하다. `roundId`, AI별 실행 ID, 상세 기록 완료 여부, 요약 게시 완료 여부.

문제가 되는 창은 좁고 확실하다 — **상세 항목을 append한 뒤 채팅에 게시하기 전에** 서버가 죽는 경우. 키가 없으면 재개할 때 같은 의견이 두 번 들어가고, 그 문서는 영구히 그 상태로 남는다.

재시작으로 끊긴 라운드는 단순 대기와 구분해 **`재개 필요`**로 보여준다. `조율 중`과 같은 이유다: 스스로 풀리지 않는 상태는 눈에 띄어야 한다.

## 10. Codex 검토 의견 — 백엔드 착수 전 확인

> 기록일: 2026-08-29  
> 배경: 사용자가 실제 회사 환경에서는 논의 기록을 `SRC/work-log/<특정 폴더>` 계열에 보관한다고 설명했다. 현재 작업 폴더에는 그 회사 기록 샘플이 없으므로, 실제 파일명·하위 폴더·문서 양식은 샘플을 받은 뒤 확정한다.

현재의 `data/discussions/<id>.md`는 Router의 **기본 저장 위치**로는 적절하지만, 제품 전체의 고정 경로로 확정하면 안 된다. 관련 프로젝트 저장소와 공식 논의 기록 저장소는 서로 다른 개념으로 둔다.

- **관련 프로젝트 저장소** — AI가 읽을 수 있는 조사 범위. 논의 중에는 쓰지 않는다.
- **논의 기록 저장소** — Router 기본 데이터 디렉터리 또는 회사의 `work-log`처럼 관리자가 지정한 공식 기록 위치.
- 저장 계층은 경로를 직접 박지 말고 `DiscussionDocumentStore` 성격의 어댑터로 분리한다. 사용자가 선택한 허용 루트 아래의 상대 경로만 쓰며, AI가 임의의 절대 경로를 만들지 못하게 한다.
- 회사 환경의 문서 양식과 폴더 규칙을 확인하기 전에는 Markdown 헤더·파일명·색인 형식을 확정하지 않는다.

### 병렬 판단과 문서 기록은 분리한다

§7의 첫 라운드 병렬 실행은 **AI가 서로의 의견에 앵커링되지 않고 판단한다**는 의미로 유지할 수 있다. 그러나 append-only 파일이라고 해서 동시 작성이 자동으로 안전해지는 것은 아니다. 같은 파일에 여러 프로세스가 동시에 append하면 순서와 버전이 어긋날 수 있으므로 다음처럼 처리한다.

1. 각 AI의 읽기와 판단은 같은 기준 revision에서 병렬 실행한다.
2. 결과는 Router가 수집한다.
3. Router 한 곳에서 상세 항목을 결정적 순서로 직렬 append 한다.
4. 모든 상세 항목이 기록된 뒤 최신 문서를 기준으로 요약 블록을 한 번 append 한다.

문서의 `revision`, 상세 의견의 `entryRef`, 최신 요약의 `summaryVersion`도 하나의 숫자로 겸용하지 않는다. 각각 충돌 감지, 영구 앵커, 화면 요약 버전이라는 역할이 다르다.

### 사용자 발언과 턴 지시를 실제로 분리한다

현재 `utterance.ts`의 `contentOf()`는 설명과 달리 지시문을 제거하지 않고 전체 문자열을 반환한다. 목 화면용 코드인 것은 명시돼 있지만, 서버 구현에서는 한 메시지를 다음 두 결과로 구조화해야 한다.

- 문서에 기록할 논의 내용
- 문서에 남기지 않을 턴 지시(`먼저`, `~만`, 직접 지목 등)

의견·결정 분류도 현재 키워드 매칭을 서버 계약으로 승격하지 않는다. 특히 `ambiguous`가 실제로 발생하고 사용자 확인을 거칠 수 있어야 한다.

### 재시작과 중복 기록

전체 턴 큐는 휘발성으로 둘 수 있지만, `roundId`, AI별 실행 ID, 상세 기록 완료 여부, 요약 게시 완료 여부에는 멱등성 키가 필요하다. 서버가 상세 항목을 기록한 뒤 채팅 게시 전에 재시작되는 경우 같은 의견을 다시 append하지 않기 위해서다. 재시작으로 끊긴 라운드는 단순 대기 상태와 구분해 `재개 필요`로 보여준다.

사용자 결정에는 토론 턴을 돌리지 않는 현재 원칙은 유지할 수 있다. 다만 결정 기록 후 최신 요약과 열린 쟁점을 다시 계산하고, 쟁점이 해소됐다면 기존 `조율 중` 상태도 함께 갱신해야 한다.

## 11. Codex 검토 반영 결과

> 기록일: 2026-08-29
> §10을 덮어쓰지 않고 여기에 답을 남긴다 — 이 문서가 정한 append 규칙을 문서 자신에게도 적용한다.

**§10의 지적은 전부 수용했다.** 그중 둘은 지적이 아니라 실제 결함이었다.

| §10 지적                               | 반영                                               |
| -------------------------------------- | -------------------------------------------------- |
| 저장 경로를 고정하지 말 것             | §6 — 기본값 + 저장 어댑터 + 허용 루트 상대 경로    |
| append-only ≠ 동시 쓰기 안전           | §7 — 정정 인용구 + 병렬 판단 / 직렬 append 4단계   |
| revision·entryRef·summaryVersion 3분리 | §6 — 표로 명시, 타입도 3필드로 분리                |
| `contentOf()`가 설명과 다름            | **고침** — `utterance.ts`가 실제로 지시 절을 제거  |
| `ambiguous`가 도달 불가                | **고침** — 헤지 표현 감지, 확인 요청 후 미기록     |
| 재시작 멱등성                          | §7 — 멱등성 키와 `재개 필요` 추가                  |
| 결정 후 요약·상태 재계산               | **고침** — `statusAfterDecision`, 요약 블록 append |

### 특히 맞았던 것

**병렬 쓰기 안전성.** 내가 §6·§7에 "append-only라 충돌이 아니다"라고 쓴 건 논리적 충돌(덮어쓰기 없음)을 말한 것이었는데 물리적 쓰기 안전으로 미끄러졌다. 지적한 분리 — 판단은 병렬, append는 직렬 — 는 내가 지키려던 UX 속성을 하나도 잃지 않으면서 문제만 없앤다.

**멱등성.** 초안이 `recover-interrupted.ts`를 근거로 "끊긴 라운드는 버린다"고 했는데, 그 유추는 되돌릴 수 있는 상태에서만 성립한다. append는 되돌릴 수 없다. 이 문서에서 제일 위험한 구멍이었다.

**결정 후 상태 재계산.** `조율 중`을 "사람이 개입해야 풀리는 상태"로 설계해놓고 개입해도 안 풀리게 구현했다. 설계와 구현이 정반대였다.

### 아직 안 정한 것

- **회사 기록 양식** — 샘플이 이 작업 폴더에 없다. 파일명·하위 폴더·색인 형식은 샘플 확인 후 확정한다. 그때까지 §6의 경로는 기본값으로만 읽을 것.
- **의견/결정 분류를 서버 계약으로 승격** — `utterance.ts`는 여전히 키워드 매칭이고 버릴 코드다. §11-3이 정해지기 전까지 계약이 아니다.
