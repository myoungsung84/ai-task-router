# 논의 스킬

> 논의방에 참여하는 모든 AI가 따르는 지침.
> Claude Code는 `.claude/skills/discussion/SKILL.md`가 이 파일을 가리킨다. Codex 등 다른 참가자도 이 파일을 기준으로 한다.

MCP 도구(`create_discussion`, `read_discussion_document`, `claim_discussion_turn`, `submit_discussion_turn`, `list_discussions`, `add_discussion_repo`)는 **바이트만 옮기고 아무것도 판단하지 않는다.** 무엇을 말할지, 입장을 유지할지, 사용자 문장이 결정인지 — 그 판단이 전부 이 문서에 있다.

기획은 `discussion-room-proposal.md`, 화면과 저장 형식은 `discussion-room-ux.md`에 있다.

## 1. 논의를 시작할 때

### 언제 만드는가

사용자가 논의를 요청했을 때만 만든다. 어려운 질문이 나왔다고 알아서 방을 파지 않는다.

논의방은 **여러 AI와 사용자가 하나의 안건을 두고 근거를 쌓는 곳**이다. 코드를 고치는 일이면 Task이고, 한 번 답하면 끝나는 질문이면 그냥 답한다.

### 무엇을 구조화하는가

방을 만들기 전에 대화에서 다음을 뽑는다.

- **제목** — 안건을 한 줄로
- **배경과 목적** — 왜 지금 이걸 정해야 하는가
- **핵심 질문** — 이 논의가 답해야 할 것
- **확인된 사실** / **미확인 사항** — 아래 §1.3을 반드시 읽을 것
- **관련 저장소** — 필수. 여러 개가 기본이다
- **참여자** — 기본은 Claude와 Codex
- **제외 범위** — 이번에 다루지 않을 것

### 확인된 사실은 가장 위험한 칸이다

**문서에 사실로 적히면 이후 모든 발언이 그 위에 쌓이고, 아무도 다시 묻지 않는다.**

- 코드에서 읽었거나, 측정했거나, 사용자가 확언한 것만 `facts`에 넣는다.
- 추정·기억·"아마 그럴 것"은 전부 `open`에 넣는다.
- 애매하면 `open`이다. 나중에 사실로 올리는 건 쉽고, 내리는 건 이미 그 위에 쌓인 뒤다.

### 저장소는 여러 개가 기본이다

논의는 대개 **여러 곳이 어떻게 얽히는지**가 안건이다. 하나만 넣지 말고 관련된 것을 모두 넣는다.

이 목록은 **조사 경계**이기도 하다. 여기 없는 저장소는 읽지 않는다. 논의 중 필요한 곳이 드러나면 `add_discussion_repo`로 추가하거나 사용자에게 요청한다.

### 만들기 전에 확인받는다

구조화한 내용을 사용자에게 보여주고 **특히 `확인된 사실` 항목을 짚어서** 맞는지 묻는다. 확인 뒤에 `create_discussion`을 호출한다.

## 2. 발언할 때

### 순서를 지킨다

1. `claim_discussion_turn` — 내 차례인지, 기준 `revision`이 무엇인지 확인
2. `read_discussion_document` — **문서 전체를 읽는다.** `agent`를 함께 넘긴다
3. 판단
4. `submit_discussion_turn` — `baseRevision`을 함께 보낸다

2번에 `agent`를 넘기면 방 화면의 `문서 읽음` 노드가 켜진다. 차례를 물은 것과 문서를 가져간 것은 다른 행동이고, 화면이 그리는 건 후자다.

`yourTurn`이 false면 아무것도 하지 않는다.

### 문서를 반드시 읽는다 — 특히 방을 만든 직후에

**논의를 만든 AI가 이 규칙을 건너뛰기 가장 쉽다.** 방금 자기가 대화에서 뽑아냈으니 다 안다고 느끼기 때문이다.

그게 정확히 금지된 것이다. 판단 근거는 채팅이 아니라 문서다. 구조화 과정에서 빠지거나 달라진 게 있으면 이때 드러나고, 그게 문서가 진짜 단일 기준인지 확인하는 첫 테스트다.

### 새 근거가 있을 때만 말한다

`grounds: true`로 발언하려면 직전 내 발언 이후에 **새로 생긴 것**이 있어야 한다.

| 새 근거다                       | 새 근거가 아니다                 |
| ------------------------------- | -------------------------------- |
| 새로 읽은 코드·문서             | 같은 주장을 다르게 표현          |
| 측정값·실행 결과                | 상대 의견에 대한 단순 동의·반대  |
| 상대가 새로 낸 근거에 대한 반박 | 이미 말한 근거의 재강조          |
| 사용자가 새로 준 정보           | 상대가 아직 답하지 않았다는 사실 |

없으면 `grounds: false`. 문서에는 아무것도 쓰이지 않고 `입장 유지`로 표시된다. **그게 정상 동작이고, 침묵이 곧 대답이다.**

### 지목받았으면 반드시 답한다

`claim`의 `addressed`가 true면 사용자가 나를 직접 물은 것이다. 이때는 `입장 유지`로 넘어가지 않는다.

새 근거가 없다면 **없다고 말한다.**

> 새로운 근거가 없어 기존 입장을 유지한다.
> 근거: 직전 발언 이후 추가된 사실·측정값이 없다.

침묵은 고장으로 읽히고, 없는 논거를 지어내는 것은 더 나쁘다. 그 사이가 정답이다.

### 메시지는 짧게, 상세는 문서에

`body`는 **결론 1줄 + 근거 1~2줄**이다.

```
수집은 유지하되 범위를 축소하는 쪽이 낫다.
근거: 재생성 비용이 수집 비용을 넘는 지점이 확인되지 않았다.
```

채팅에 근거를 길게 풀면 사람이 그걸 읽고 판단하기 시작하고, 그러면 "문서가 단일 기준"이 말로만 남는다. 인용은 `sources`에 경로로 넣는다.

앞선 발언을 참조할 때는 항목 번호(`#47`)를 쓴다. 문서는 append-only라 번호가 변하지 않는다.

### 요약 갱신을 제안할 때

`summaryDelta`로 `facts` / `agreed` / `open`을 올릴 수 있다. Router가 라운드 종료 시 한 번만 반영한다.

- 넘기는 배열은 **그 항목의 전체 목록**이다. 기존 것을 지우지 않으려면 함께 담는다.
- 생략하면 기존 요약이 그대로 유지된다. 확신이 없으면 생략한다.
- `decisions`는 건드리지 않는다. 사용자 결정만 들어가는 칸이다.

### `stale`이 true로 돌아오면

내가 읽은 뒤에 문서가 바뀌었다는 뜻이다. 내 결론이 그 변화에 영향받는지 판단하고, 받는다면 다시 읽고 의견을 조정한다. 자동으로 취소되지 않는다 — 판단은 내 몫이다.

## 3. 하지 않는 것

**논의 중 코드에 손대지 않는다.** 파일 수정, 테스트 실행, 브랜치 변경, 커밋, 푸시 전부 금지다. 후속 구현이 필요하면 사용자가 별도로 Task를 만든다.

**등록되지 않은 저장소를 조사하지 않는다.** 필요하면 추가를 요청한다.

**사용자의 침묵·질문·단순 동의를 결정으로 추정하지 않는다.** 결정은 사용자가 명확히 말했을 때만 결정이다. 애매하면 묻는다.

**근거 없이 빠르게 동조하지 않는다.** 상대 말이 맞아 보인다고 바로 접는 것은 반복 반박만큼 나쁘다. 수용한다면 무엇을 근거로 수용하는지 쓴다.

**같은 주장을 반복하지 않는다.** 상대가 내 근거에 답하지 않았다는 사실 자체는 새 근거가 아니다.

**최종 결론을 확정하지 않는다.** 결정권은 사용자에게 있다.

## 4. 의견을 바꿀 때

바꾸는 것은 좋은 일이다. 다만 **무엇 때문에 바뀌었는지** 쓴다.

```
측정 기록이 없다는 지적을 수용한다. 수집은 유지하되 범위를 축소하는 쪽으로 의견을 바꾼다.
근거: 재생성 비용이 수집 비용을 넘는 지점이 확인되지 않았다.
```

이전 발언은 문서에 그대로 남는다. 지우거나 고치지 않는다 — 의견이 어떻게 움직였는지가 논의의 내용이다.
